# تمريضي | خطة أداء قاعدة البيانات والاستعلامات — v0.2

## ما الذي تغيّر فعليًا؟

1. `002_query_indexes.sql`: فهارس مركّبة للصفحات والتصفية وFKs، وفهرس جغرافي موجود مسبقًا. لا فهرسة مكررة للمفاتيح الأساسية `PRIMARY KEY` أو المفاتيح الفريدة `UNIQUE`، لأنها تفهرس تلقائيًا.
2. `requests.service.ts` و`admin.controller.ts` و`nurses.service.ts`: قوائم محددة بـ 20 سجلًا افتراضيًا (حد أقصى 50) مع `nextCursor` و`hasMore`. الترتيب `created_at DESC, id DESC` يضمن استقرار المؤشر وتسمح الصيغة بنقل الدقة الميكروثانية لتاريخ PostgreSQL، دون خسارة أجزاء الثانية عبر JS Date.
3. `apps/worker/src/main.ts`: إرسال الطلب إلى الممرضين المتاحين عبر CTE set-based: إدراج عروض الطلبات وأحداث Outbox في **استعلام SQL واحد** لكل موجة بدل 2×عدد الممرضين. تحديث أحداث Outbox المنشورة مجمّع أيضًا.
4. `ReferenceCacheService`: Cache-aside بRedis لخدمات الكتالوج العامة فقط، لمدة 300 ثانية، مع إبطال إصدار المفتاح عند تعديل عرض الخدمة، والعودة لقاعدة البيانات إن تعطل Redis.
5. شاشة لوحة الإدارة أصبحت تعرض أول صفحة فقط وزر «تحميل المزيد»؛ أُزيل polling كل 15 ثانية.

## صيغة API الجديدة (Breaking change)

- `GET /v1/requests/mine?limit=20&cursor=...`
- `GET /v1/admin/requests?limit=20&cursor=...&status=OFFERING`
- `GET /v1/admin/nurses?limit=20&cursor=...`
- `GET /v1/nurse/me/history?limit=20&cursor=...`

الاستجابة:

```json
{
  "items": [{"id":"...","status":"COMPLETED","created_at":"..."}],
  "hasMore":true,
  "nextCursor":"opaque.signed"
}
```

قاعدة مهمة: لا تفرض على التطبيق طلب كل الصفحات لعرض قائمة واحدة. استخدم زر "المزيد" أو infinite scrolling عند الاقتراب من نهاية القائمة، مع إلغاء التحميل السابق عند تبديل الفلاتر. مؤشر الصفحة مربوط بالتصفية والمستخدم وموقّع، فلا يجوز تمريره إلى مستخدم أو قائمة أخرى.

## سياسة Indexing

- `PRIMARY KEY` / `UNIQUE`: موجودة تلقائيًا، **لا تنشئ فهرسًا إضافيًا لنفس المفتاح**.
- `FOREIGN KEY`: PostgreSQL لا ينشئ فهرسًا تلقائيًا للعمود التابع؛ أضيفت الفهارس المناسبة لاستعلاماتنا والحذف/التحقق من العلاقات.
- `requester_user_id, created_at DESC, id DESC` و`status, created_at DESC, id DESC`: تخدم فلاتر الطلبات وkeyset.
- GiST على `nurse_locations.location` لخدمة `ST_DWithin`.
- فهارس جزئية للممرضين المتاحين وأحداث Outbox المستحقة، لتصغير الحجم قدر الإمكان.
- لا تضف فهرسًا لكل عمود: الفهارس تبطئ INSERT/UPDATE وتزيد حجم التخزين والـVACUUM. راقب `pg_stat_user_indexes` و`pg_stat_statements` حيث متاح.

**تنبيه ترحيل:** ملف `migrate.mjs` ينفذ ملفات SQL داخل Transaction. لذلك لا تضع `CREATE INDEX CONCURRENTLY` داخل الملف 002. في قاعدة إنتاجية كبيرة، أنشئ الفهارس مسبقًا يدويًا باستراتيجية غير محجوبة للكتابة `CONCURRENTLY` خارج أي معاملة، بعد أخذ نسخة احتياطية ومراجعة القياسات ثم سجّل الترحيل كمنفّذ وفق إجراء نشر مضبوط. لا تستخدم `IF NOT EXISTS` كدليل أن الفهرس الصحيح موجود؛ تحقق من تعريفه.

## كيف نمنع N+1؟

- لا تُنشئ `db.query` داخل حلقة نتائج لعرض اسم الخدمة/المريض/الممرض. استعلم عن الكيانات المرتبطة ب`JOIN` أو Bulk Lookup على قائمة IDs محددة، ثم اربطها بالذاكرة.
- لا تعمل `for each nurse -> INSERT offer -> INSERT outbox`: أصبح ذلك CTE ذريًا.
- لا تكثر من الأعمدة عبر `SELECT *` في تقارير القوائم؛ استخدم DTO بأعمدة محدودة.
- حافظ على صف واحد لكل طلب باستخدام قيد `uq_active_assignment_per_request` عند الربط مع الإسناد النشط.
- **قاعدة الاختبار:** عدد استعلامات SQL للصفحة ذات 10 عناصر والصفحة ذات 50 عنصرًا يجب أن يبقى ثابتًا بالنسبة إلى بيانات العرض المرتبطة، وليس 1+N.

## سياسة الكاش

| البيانات | TTL | قواعد التعامل |
|---|---:|---|
| كتالوج الخدمات المعروض للجمهور | 300 ثانية | إبطال الحدث عند تعديل ظهور الخدمة + انتهاء صلاحية احتياطي |
| تصنيفات الخدمات/الأحياء لاحقًا | 300–1800 ثانية | يمكن إضافتها بعد وجود جداول فعلية وتحليل الاستخدام |
| فحص مؤهلات الممرض ورخصته | 0 | قراءة موثوقة مباشرة عند قبول الطلب |
| وضع الطلب والقبول وعروض الممرض | 0 | لا تستخدم كاش ذاكرة طويلة، فهي حالات متغيرة وأمنية |
| المواقع الحية للمرضى والممرضين | 0 | بث لحظي مع توثيق ومدة قصيرة وليس كتالوجًا ثابتًا |
| أرصدة المحفظة والمعاملات | 0 | المرجع مزود الدفع + السجل المالي، ولا تخزن أرقامًا مفترضة بالكاش |

> في النموذج الحالي الـTTL هو حد تقريبي لمدة بقاء القيمة في Redis، وليس ضمانًا قويًا للقراءة الخطية المتسقة. التعديل الإداري يصدر `cache.invalidate` عبر Outbox لنسخ API الأخرى، مع إبطال مباشر لنسخة الخادم التي أجرت التعديل. وقت انقطاع Redis يعود الطلب لقراءة DB؛ عند التعافي قد تظهر بيانات قديمة حتى انتهاء TTL إذا تعذر تسليم حدث الإبطال.

## مؤشرات أداء مقترحة للاختبار — ليست قياسات حقيقية

- `API GET /v1/requests/mine`: P95 دون 250ms وقت المعالجة على الخادم في بيئة اختبار فيها 100k طلب.
- `API GET /v1/admin/requests`: P95 دون 300ms بالفهارس ومن غير فلاتر تتسبب بمسح كامل.
- `catalog/services`: cache hit rate ≥ 80% بعد فترة الإحماء؛ DB fallback عند توقف Redis.
- `dispatch wave SQL query count`: استعلام موحد للإدراج بغض النظر عن كون المرشحين 2 أو 20.
- قياس `EXPLAIN (ANALYZE, BUFFERS)` على بيانات واقعية مماثلة؛ راقب `Rows Removed by Filter`، و`Sort`، و`Seq Scan`، والـbuffer reads. ليس كل Seq Scan خطأ: عند الجداول الصغيرة قد يكون أفضل.
- قارن زمن P50/P95/P99 وحجم نتائج الشبكة وعدد الاستعلامات قبل/بعد، مع ضبط warm/cold cache.
