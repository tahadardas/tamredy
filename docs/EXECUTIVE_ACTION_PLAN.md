# المرحلة الأولى: تثبيت المعمارية وربط جميع التطبيقات

## 1. التقنيات الواجب المحافظة عليها

- Patient App: Flutter + Dart.
- Nurse App: Flutter + Dart.
- Admin Dashboard: React + TypeScript.
- Backend: Node.js + NestJS + TypeScript.
- Database: PostgreSQL + PostGIS.
- Cache: Redis.
- Background Jobs: BullMQ.
- Realtime: Socket.IO.
- Push Notifications: Firebase Cloud Messaging.
- Maps: Google Maps ضمن طبقة تجريد تسمح بتبديل المزود.
- Deployment: Docker + Nginx.
- Shared API Contract: OpenAPI مع DTOs محددة الأنواع.

استخدم إصدارات مستقرة ومتوافقة مع المشروع. لا تنفذ ترقيات جماعية للمكتبات دون ضرورة، ولا تكسر API يعمل حاليًا.

1. حافظ على شروط التفعيل والاعتماد السريري، ولا تجعل كل الخدمات منشورة تلقائيًا.
2. اجعل لوحة الإدارة تعرض حالة كل خدمة بوضوح: مسودة، بانتظار الاعتماد السريري، منشورة، موقوفة.

6. أضف مسارًا منفصلًا للخدمات التي تتطلب وصفة أو تحققًا سريريًا، مع ظهور معلوماتها للمريض فقط إذا كانت سياسة النشر تسمح، ومنع الحجز قبل اكتمال المتطلبات.
7. لا تُغيّر `requires_prescription` إلى `false` لإخفاء المشكلة.
8. اجعل استجابة الخدمات تحتوي على الحقول الضرورية للواجهة، مثل المعرف والاسم والوصف والسعر والمدة وحالة الإتاحة والمتطلبات المسموحة للعرض.
9. أضف كود خدمة ثابتًا ووصفًا مناسبًا وأيقونة أو تصنيفًا صريحًا، ولا تعتمد في Flutter على ترتيب الخدمة داخل المصفوفة لاختيار الأيقونة.
10. استخدم نماذج Dart typed بدل الاعتماد على خرائط ديناميكية غير محققة.
11. وفر Endpoint عامًا محدودًا لعرض كتالوج الخدمات قبل تسجيل الدخول إذا كان هذا جزءًا من تجربة الاستخدام، مع بقاء عمليات الحجز محمية بالمصادقة.
12. اجعل الخدمات الموقوفة تختفي من قائمة الحجز وفق سياسة النشر، دون التأثير في الفواتير والطلبات السابقة المرتبطة بها.

## 8. إصلاح قبول الممرض والذهاب إلى المريض

يوجد خلل في:

`apps/nurse_app/lib/controller.dart`

حيث ينتقل التطبيق إلى `enRoute` بعد قبول العرض دون إرسال `depart`.

نفّذ التسلسل التالي:

1. يستقبل الممرض العرض.
2. يضغط «قبول».
3. ينفذ التطبيق:

`POST /v1/nurse/offers/:offerId/accept`

4. يتحقق من نجاح الإسناد وحصوله على `assignmentId`.
5. ينفذ:

`POST /v1/nurse/assignments/:id/depart`

6. ينتظر نجاح العملية.
7. يحدّث حالة الواجهة إلى «في الطريق».
8. يبدأ إرسال الموقع المباشر وفق أذونات الجهاز.
9. يفتح خريطة الملاحة داخل التطبيق مع خيار Google Maps الخارجي.

عند فشل `depart`:

- لا تعرض أن الممرض أصبح في الطريق.
- استعلم عن الحالة الحقيقية للإسناد.
- أظهر رسالة واضحة قابلة للتنفيذ.
- امنع تكرار القبول أو إنشاء إسناد جديد عن طريق الخطأ.

# المرحلة الرابعة: محرك توزيع الطلبات ومنع التضارب

## 12. المحافظة على First Qualified Accept Wins

يجب الحفاظ على القاعدة التالية:

**أول ممرض مؤهل يتمكن من تثبيت القبول في قاعدة البيانات يفوز بالطلب وحده.**

لا تستبدل ذلك بآلية اختيار الممرض من قبل المريض.

المطلوب:

- الحفاظ على PostgreSQL Transactions.
- الحفاظ على `SELECT FOR UPDATE`.
- الحفاظ على القيود الفريدة الجزئية للإسنادات النشطة.
- منع قبول طلبين نشطين من الممرض نفسه.
- منع قبول الطلب نفسه من ممرضين.
- إعادة فحص الترخيص والتأهيل وحالة التوفر لحظة القبول.
- جعل القبول المتكرر من الممرض الفائز آمنًا وقابلًا للإعادة.
- استخدام Transactional Outbox لنشر الأحداث بعد نجاح المعاملة.

## 16. إعادة المزامنة

أكمل Realtime باستخدام Socket.IO وREST معًا.

عند:

- إعادة اتصال الإنترنت.
- فتح التطبيق.
- العودة من الخلفية.

يجب إعادة الاستعلام عن البيانات الحقيقية من API.

لا تعتمد على وصول جميع أحداث WebSocket، ولا تسمح لحدث قديم بإرجاع الطلب إلى مرحلة سابقة.

استخدم `eventId` و`version` لمنع تطبيق الأحداث القديمة أو المكررة.

## 30. منع N+1 Query

يُمنع تنفيذ استعلام منفصل لكل عنصر داخل قائمة.

نفّذ:

- JOINs صحيحة.
- Batch Queries.
- `INSERT ... SELECT` للعمليات الجماعية.
- جلب البيانات المرتبطة بدفعات.
- منع استعلامات العد أو التقييم أو الأرباح المتكررة لكل صف في قائمة الإدارة.
- فصل الاستعلامات الثقيلة عن استعلامات القوائم السريعة.
- استرجاع الأعمدة المطلوبة فقط بدل `SELECT *` في القوائم الكبيرة.

أضف اختبارات تكامل تتحقق من أن عدد الاستعلامات لا يزداد خطيًا مع عدد عناصر الصفحة.

## 31. Pagination

اعتمد:

- Keyset/Cursor Pagination للقوائم الكبيرة.
- ترتيب ثابت باستخدام التاريخ والمعرف الفريد.
- Cursor مرتبط بالمستخدم والفلاتر.
- حجم صفحة افتراضي 20.
- حد أقصى 50.
- معالجة انتهاء النتائج.
- دعم إعادة التحميل وإلغاء الطلبات السابقة.
- عدم استخدام OFFSET عميق مع مئات آلاف السجلات.

تأكد من إكمال Pagination في تطبيق المريض والممرض ولوحة الإدارة، وليس في API وحده.

## 32. الكاش

اعتمد Redis Cache-Aside للبيانات المرجعية المناسبة مثل:

- كتالوج الخدمات المنشور.
- التصنيفات.
- المحافظات والمناطق.
- إعدادات عامة آمنة للعرض.
- القيم المرجعية قليلة التغير.

المطلوب:

- Cache Keys محددة.
- TTL معقول.
- Cache Invalidation عند التعديل.
- منع البيانات القديمة من الاستمرار بعد تعديل الإدارة.
- إمكانية العودة إلى PostgreSQL عند توقف Redis.
- منع تسرب الكاش بين المستخدمين.

لا تعتمد على الكاش باعتباره المرجع النهائي لـ:

- حالة الطلب.
- الإسناد النشط.
- موقع المريض الخاص.
- الرصيد النقدي.
- الفاتورة.
- صلاحية الترخيص.
- صلاحيات المستخدم الحساسة.

## 33. مراقبة الأداء

- Structured Logging.
- Correlation ID.
- SQL Duration.
- API Response Time.
- Worker Queue Lag.
- Redis Hit/Miss.

- تنبيهات للأعطال الحرجة.

ألغِ أي Polling غير ضروري كل بضع ثوانٍ، واستعمل Realtime Events مع إعادة مزامنة عند الحاجة.

## أسلوب العمل الإلزامي

ابدأ بالتعديل المباشر على الملفات الموجودة.

لا تُنشئ تقريرًا تحليليًا قبل التنفيذ، ولا تعرض خططًا بديلة، ولا تطلب مني اتخاذ قرارات تقنية حُسمت في هذه الوثيقة.

أنجز بالترتيب:

**إصلاح التكوين والاتصال ← إصلاح الخدمات ← إصلاح دورة الطلب ← إصلاح التوزيع والإشعارات ← إصلاح الخرائط ← إصلاح الحسابات والتقيمات ← تحسين الواجهات ← تحسين قاعدة البيانات والأداء ← تعزيز الأمان ← الاختبارات النهائية ← معالجة الإخفاقات ← التسليم.**

إذا كشف الاختبار عن مشكلة، أصلح السبب الجذري ثم أعد الاختبار.

لا تضع `TODO` أو `Mock` أو `Placeholder` داخل وظيفة مطلوب أن تكون مكتملة، ولا تعدّ الاختبارات التي لم تعمل اختبارات ناجحة.

إذا تعذر تشغيل خدمة خارجية، اذكر العائق تحديدًا مع المحافظة على الشيفرة الصحيحة، ولا تختلق نتيجة نجاح.

**الهدف النهائي: منصة تمريضي مترابطة، سريعة، آمنة، سهلة الاستخدام، مستقرة، وقابلة للتوسع؛ بحيث تعمل التطبيقات الثلاثة مع الباك إند وقاعدة البيانات كنظام واحد حقيقي، وليس ثلاث واجهات منفصلة تحتوي على بيانات تجريبية.**

ابدأ التنفيذ الآن، واحرص على إنجاز الإصلاحات الفعلية قبل الانتقال إلى دورة الاختبار النهائي.
